This document explains what every file does and how the parts talk to each other. For setup and running, see [README.md](README.md).

If you renamed a file, look for the entry with the same job.

## 1. The big picture

Fruttree has two programs that run side by side:

| Program | Language | Folder | Port | Job |
|---|---|---|---|---|
| Website | JavaScript (React + Vite) | `src/` | 5173 | Draws the map, popups and controls |
| API | Python (FastAPI) | `ml/` | 8000 | Looks up trees in the database and predicts soil dryness |

The website also calls Open-Meteo directly for weather and air quality.

### What happens when you use the map

**Moving or zooming the map**

1. `TreeMap.jsx` notices the map moved and reports the visible area and zoom level.
2. `App.jsx` keeps that in its state and passes it to `useFruitTree.js`.
3. The hook asks the API: individual trees if zoomed in (`/trees`), circles if zoomed out (`/clusters`).
4. `fruitTree.js` converts the raw answer into objects the app uses.
5. `TreeMap.jsx` draws them as markers, or `ClusterMarkers.jsx` draws the circles.

**Clicking a tree**

1. The popup (`FruitTreeInfoPopup.jsx`) opens and starts four separate requests, so a failure in one never breaks the others:
   - tree details from your API (`/trees/{id}`)
   - weather from Open-Meteo (`WeatherInfo.jsx`)
   - dryness chance from your API (`/watering`), shown by `WateringRisk.jsx`
   - air quality from Open-Meteo (`AirQualityInfo.jsx`)

### The layers inside `src/`

Each kind of file has one job. This keeps changes small: if an API changes its field names, only one file needs fixing.

```
services/   talk to an API (the only files that call fetch)
models/     turn raw API data into objects the app uses (the only files that know field names)
hooks/      decide when to fetch, keep loading/error state, cache results
utils/      small helper functions with no React and no network
components/ what you see on screen
data/       fixed lists (fruit emojis)
```

## 4. The website: `src/`

### Entry and styling

| File | What it does |
|---|---|
| `main.jsx` | Starts React: finds `#root` in `index.html` and draws `<App />` into it. Also loads `index.css`. |
| `App.jsx` | The top-level component. Holds the app's state (your own trees, the selected fruit, whether you are adding a tree, the visible map area), calls `useFruitTree`, draws the header, and floats a status message ("Loading trees...") over the map. |
| `App.css` | Styles for the header, controls, the map area, the floating status label, tree emoji markers, circles, the popup, the dryness bar, and the air quality badge. |

| `config.js` | The settings in one place: API address, `MIN_ZOOM`, `MAX_TREES`, `CLUSTER_ZOOM_STEP`, and the weather and air quality URLs. |

### Settings in `config.js`

| Setting | Meaning |
|---|---|
| `API_URL` | Where your Python API runs (`http://localhost:8000`). |
| `MIN_ZOOM` | From this zoom level and closer the map shows individual trees. Further out it shows circles. |
| `MAX_TREES` | The most trees requested at once. |
| `CLUSTER_ZOOM_STEP` | How many zoom levels a click on a circle zooms in. |
| `WEATHER_URL`, `WEATHER_PAST_DAYS`, `WEATHER_FORECAST_DAYS` | Open-Meteo weather endpoint and how many days around today to load. |
| `AIR_QUALITY_URL` | Open-Meteo air quality endpoint. |

### `components/` (what you see)

| File | What it does |
|---|---|
| `TreeMap.jsx` | The map itself. Draws the OpenStreetMap tiles, the public trees (each with a popup), your own trees, and the circles. Contains two invisible helpers: `ViewWatcher` (reports the visible area and zoom after every move) and `ClickHandler` (reports clicks so you can place a tree). |
| `ClusterMarkers.jsx` | Draws the green circles with tree counts when zoomed out. Clicking one flies the map closer. |

| `WeatherInfo.jsx` | Current temperature and conditions, wind, rain over the last 7 and next 3 days, the dryness bar, and the simple rule-of-thumb watering advice. Used in both kinds of popup. |
| `WateringRisk.jsx` | The machine learning result: "Chance the soil is dry tomorrow: 35% (Medium)" with a coloured bar. It hides itself if the API or model is unavailable. |
| `AirQualityInfo.jsx` | A coloured badge (Good to Extremely poor), the European AQI number, and PM2.5 and PM10 values. |

### `data/`

| File | What it does |
|---|---|
| `fruits.js` | The one list of fruits and their emojis. It feeds the dropdown, the icons of your own trees, and the guess of which emoji a public tree gets (by matching words in its name). Also holds the fallback emoji (🌳). |

### `hooks/` (when to fetch, loading and error state)

| File | What it does |
|---|---|
| `useFruitTree.js` | Given the visible area and zoom, fetches either trees or circles. Cancels outdated requests while you pan, and keeps the old markers on screen while new ones load so the map does not flash. |
| `useLocationDetails.js` | Fetches one tree's full details when its popup opens. Remembers results so reopening is instant. |
| `useWeather.js` | Fetches weather for a position. Cached for 30 minutes, and nearby trees share one request. |
| `useWatering.js` | Fetches the machine learning dryness estimate from your API for a position. Cached per place. |
| `useAirQuality.js` | Fetches air quality for a position. Cached for 30 minutes, with nearby trees sharing a request because the data is coarse. |

| File | What it does |
|---|---|
| `fruitTree.js` | `toTree` makes a map marker object from an API row, `toCluster` makes a circle, and `toDetails` makes the popup details (season text, access, update date, link). This is the only place that knows the API's field names. |
| `weather.js` | Turns Open-Meteo's weather answer into current conditions, a list of days, and the rain totals. |
| `airQuality.js` | Turns Open-Meteo's air quality answer into the numbers and label shown in the popup. Returns nothing when a place has no data. |

| File | What it does |
|---|---|

## 5. The Python side: `ml/`

### Scripts you run once (or occasionally)

| File | What it does | Run with |
|---|---|---|
| `build_db.py` | Reads `types.csv` and the huge `locations.csv` in chunks, joins each tree to its fruit name, drops hidden rows, and saves everything in `trees.db` (SQLite) with indexes for fast lookups. | `python ml\build_db.py` |
| `build_clusters.py` | Counts trees per grid cell at five zoom levels and saves the counts as small tables in `trees.db`. This is what makes the zoomed-out circles instant. | `python ml\build_clusters.py` |
| `train_watering.py` | Picks real tree locations from the database, downloads their historical weather and soil moisture, builds the training data, trains and calibrates the model, tests it on places it has not seen, and saves `water_model.pkl`. | `python ml\train_watering.py` |

### The API: `tree_api.py`

Run it with `uvicorn tree_api:app --reload --port 8000` from inside the `ml` folder.

| Endpoint | Returns |
|---|---|
| `GET /` | A message saying the API is running. |
| `GET /trees?south&west&north&east&limit` | Trees inside the visible area (id, position, fruit name). |
| `GET /clusters?south&west&north&east&zoom` | Circles (position and count) for the visible area at that zoom. |
| `GET /trees/{id}` | Everything known about one tree (description, season, access, address, last update). |
| `GET /watering?lat&lng` | `{ probability, percent, level }`: the chance the soil near that point is dry tomorrow. Returns 503 until the model exists. |
| `GET /docs` | An automatic page where you can try every endpoint. |

On start-up it checks that the database and circle tables exist and stops with a clear message if not. The model is optional.

### Shared code: `features.py`

Defines how weather becomes the model's inputs (`build_features`). **Both the training script and the API import this file**, so the model always receives data prepared the same way it was trained on. Changing a feature means changing it here and retraining.

### Data and generated files (not in git)

| File | What it is |
|---|---|
| `types.csv` | Falling Fruit's list of fruit types and their names in many languages. |
| `locations.csv` | Falling Fruit's full list of trees (about 670 MB). |
| `trees.db` | Your SQLite database built from the two CSVs: the `trees` table plus the `clusters_0` to `clusters_4` tables. |
| `water_model.pkl` | The trained model, its calibrator, and the list of features it expects. |
| `cache/` | One small CSV per training location, so interrupted training can resume, plus `locations.csv` listing which places were chosen. Delete the folder to start training from scratch. |

## 6. The two watering numbers

The popup shows two different estimates on purpose.

### The rule of thumb (`src/utils/waterCalc.js`)

A fixed bucket calculation using Open-Meteo weather for the last 7 days and the forecast:

- Each day the soil loses `evapotranspiration × 0.8` millimetres of water.
- Each day it gains rain, but only when more than 2 mm fell.
- The bucket holds at most 30 mm. When 15 mm or more has been lost, it says to water.

It gives one of: "Water today", "Water on [date]", or "No watering needed this week". The same numbers apply to every tree in the world, and it assumes the soil was full a week ago.

### The machine learning estimate (`ml/`)

- **Question it answers:** will the root-zone soil (7 to 28 cm deep) be unusually dry tomorrow? "Dry" means among the driest 20% of days at that place, so different soils and climates are comparable.
- **Labels:** from Open-Meteo's modelled soil moisture (ERA5-Land) for 40 real tree locations over 2020 to 2025. This is data the rule of thumb never saw, so the model learns something new rather than copying the formula.
- **Inputs (features):** rain over 7 and 14 days, evapotranspiration over 7 days, temperature, days since a rainy day, forecast rain for the next 3 days, month, and latitude. Soil moisture itself is not an input, so the app only needs the normal weather forecast to make a prediction.
- **Model:** a gradient boosting classifier, calibrated with isotonic regression so that "70%" means about 70 out of 100 similar days.
- **Testing:** places are split into training, calibration and test groups, so it is scored on places it has never seen. The script prints its score next to the rule of thumb's score so you can see whether the ML actually helps.

Reading the percentage: because "dry" is defined as the driest 20% of days, an average day gives about 20%. High numbers appear during real dry spells, mostly in summer. It is not a number of litres, and it does not know your tree's species, shade or irrigation.

## 8. Ideas for next steps

- **Save your own trees.** Right now they live in React state and vanish on refresh. A table in `trees.db` plus an endpoint to add and list them would keep them.
- **"I watered it" and "it was dry / fine" buttons.** These create real labels, which are better training data than modelled soil moisture. The existing training pipeline can take them in.
- **Use the fruit type** as a model feature, since different trees need different amounts of water.
- **Pollen** from Open-Meteo's air quality API, for European locations.
- **Deploy.** The API and database need a host that runs Python, and the website can be built with `npm run build` and hosted as static files.
